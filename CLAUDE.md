# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Общее

PWA-метроном для музыкантов. v2 — полная перестройка с нуля (2026-09-27,
см. `../metronom-v2-plan.md` для истории решений). TypeScript + Vite,
**без React, без Tailwind**, без собственного сервера. Вход — через Google
(Firebase Auth), данные и живая синхронизация — Firebase Firestore, всё в
аккаунте пользователя. Статика деплоится на тот же домен
Hostinger, что и раньше.

Если ищете описание архитектуры v1 (React + Express + MySQL) — она удалена
целиком, см. `git log` до коммита `v2 reset` и `../metronom-v2-plan.md`.

### Тесты

`tests/audioEngine.test.ts` — единственный тест-файл. Node-овский `node --test`
(через `tsx`, без отдельного тест-раннера) с самодельными заглушками
`AudioContext`/`fetch`/`requestAnimationFrame` (Node не умеет Web Audio) —
проверяет счёт долей/тактов, самоостановку непетлевой песни, то, что смена
BPM во время игры реально влияет на тайминг, а не только на следующий
`start()`, круг бита по его длине, `stepsPerBeat` и биты/филлы в секциях
(что прозвучало — по частоте запасного осциллятора инструмента). См. комментарии в файле — там же объяснение неочевидных таймингов
теста.

Кроме этого — `npm run build` (типы + сборка) перед любым коммитом.

## Архитектура кода

### Экраны и роутинг

Без React → без React Router. `router.ts` — самописный: путь → функция
рендера (`history.pushState`, паттерны `/song/:id`). `app.ts` — единственное
место, где роутер связывается с экранами; держит один `AudioEngine` на всё
приложение и общий хедер/футер (`components/appHeader.ts`,
`components/appFooter.ts`).

Маршруты: `/metronome`, `/playlist`, `/song/:id`, `/song/:id/pattern`,
`/settings`, `/beats`, `/beats/:id`. Всё остальное (включая `/`) редиректит
на `/metronome`.

`appHeader.ts` — назад/отмена всегда слева (иконка), заголовок по центру,
опциональный `rightAction` (иконка) справа — используется `/beats/:id` для
иконки сохранения. Экран не может напрямую подёргать чужую иконку в шапке
(шапка — в `app.ts`, экран монтируется отдельно): маршрут в `app.ts` держит
`let requestX`, передаёт `(fn) => { requestX = fn }` экрану третьим/четвёртым
параметром, экран при монтировании один раз кладёт туда свою функцию —
см. `/beats/:id` + `beatEditorScreen.ts` (`onRegisterSave`) как образец, если
понадобится ещё одна кнопка в шапке у другого экрана.

**DOM-структура — строго `#app (div) > div.app-header, div.screen, div.app-footer`**
(ровно три div-а, без лишней вложенности; никаких `<header>`/`<main>`/`<footer>`
— осознанное требование, не рефакторить обратно на семантические теги).
`#app` растягивается на весь экран устройства (`100dvh`, см. `tokens.css`) и
является flex-колонкой; `.app-header`/`.app-footer` — обычные flex-дети
(`flex-shrink: 0`, НЕ `position: fixed` — так было раньше, отказались),
`.screen` — `flex: 1; overflow-y: auto` и сам скроллит контент, если он не
помещается, а хедер/футер остаются на месте. `app.ts` хранит `headerEl`/
`footerEl` как переменные и на каждый рендер шапки/футера подменяет их
целиком через `replaceWith(...)` (не через mount-в-пустую-обёртку) — так
структура остаётся "три div-а — прямые дети `#app`", а не "div, содержащий
div".

### Состояние

`state/appState.ts` — простой pub/sub (не Redux, не фреймворк): один объект
`AppState`, `subscribe(cb)` на изменения, `patchState()`/`saveSongs()` и
т.д. на запись. Экраны сами решают, что перерисовывать при уведомлении —
никакой виртуальный DOM ничего не диффит за них.

**Горячий путь — исключение из этого правила.** Подсветка текущей доли
(`screens/metronomeScreen.ts`), текущего шага паттерна
(`screens/patternScreen.ts`) и сетки долей секций песни
(`screens/songScreen.ts`) обновляются НАПРЯМУЮ в DOM из
`engine.onPlaybackState(...)`, в обход `appState`/перерисовки экрана —
иначе на 24 кадрах в секунду есть риск, что рендер собьёт аудио-тайминг
(тот же принцип, что был в v1 с React, просто без React в середине).

### Построение DOM

Без фреймворка — `dom.ts` даёт `h(tag, props, ...children)` (тонкая
обёртка над `document.createElement`, не виртуальный DOM) и `mount()`
(заменить детей контейнера). Экраны и компоненты используют только это,
не пишут `document.createElement` россыпью.

### Дизайн-система

`design/tokens.css` — единственный источник цвета/отступов/радиусов/
типографики, CSS custom properties. Тема переключается атрибутом
`data-theme` на `<html>` (`state/appState.ts` → `setThemeId`). Сейчас одна
тема (Minimal) — добавление второй (`light`/`dark`) означает **только**
новый блок `[data-theme="..."]` в `tokens.css`, компоненты не трогаются
(так и задумано, см. `metronom-v2-plan.md`).

`design/components.css` — каталог переиспользуемых классов (`.btn`,
`.icon-btn`, `.card`, `.input`, `.list-row`, `.beat`, `.step`, `.badge`,
`.app-header`, `.app-footer`, `.sheet`). **Правило**: перед новым экраном —
искать подходящий класс здесь, использовать его, а не писать инлайн-стиль
с нуля. Новый переиспользуемый элемент — сюда же, в комментарий-список
в начале файла.

**Частый источник бага** (уже наступали): у модификатора (`.btn--accent`,
`.icon-btn--danger` и т.д.) и у `:hover`/`:active` на базовом классе
(`.btn:hover`) одинаковая специфичность CSS (один класс = один класс+один
псевдокласс на самом деле ВЫШЕ — `.icon-btn:hover` специфичнее
`.icon-btn--accent`!). Если у модификатора нет своего `:hover`-переопределения,
дефолтный hover-фон побеждает акцентный цвет, и светлая иконка становится
не видна на светлом фоне. Добавляя новый цветной вариант кнопки — сразу
добавить и его `:hover`.

### Аудио-движок

`engine/audioEngine.ts` + `engine/sampleLoader.ts` — тот же алгоритм, что
был в v1: `setTimeout` каждые 25ms планирует ноты на 100ms вперёд через
`AudioContext.currentTime`; события для UI кладутся в очередь и
применяются отдельным `requestAnimationFrame`-циклом. Фабричные функции с
замыканиями вместо React-хука (`createAudioEngine()`), `{ current }`-объект
вместо `useRef`, колбэки (`onPlaybackState`, `onPlayingChange`, ...) вместо
`useState`.

Один `AudioContext` на всё приложение — создаётся один раз через
`ensureAudioContext()` внутри `audioEngine.ts` (при создании движка, чтобы
декодирование сэмплов не зависело от того, выбрана ли песня — см. ниже) и
переиспользуется и для декодирования, и для воспроизведения. Не создавать
второй через `new AudioContext()` в другом месте — сэмплы, декодированные
через один контекст, всё ещё должны воспроизводиться, но плодить лишние
контексты незачем.

**Изменение BPM во время игры** применяется без остановки/перезапуска —
естественное следствие того, что `schedule()` читает `bpm` из замыкания на
каждой итерации, а не из захваченных при последнем вызове параметров (в
v1 с `useCallback` это было не так, BPM обновлялся только после
стоп/старта). Не буквально мгновенно — уже запланированная на старом
темпе доля довисит, новый темп стартует со следующей. См.
`tests/audioEngine.test.ts`.

**samplesLoaded не завязан на выбор песни.** В v1 `preloadAllSamples()`
запускался только при выборе песни — значит голый метроном без песни был
неиграбелен (кнопка Play заблокирована до `samplesLoaded`). В v2 движок
декодирует все сэмплы сразу при создании (`createAudioEngine()`), не
дожидаясь песни — метроном первая фича по плану, должна работать без неё.

**Гейн у синтезированного звука — обязательно `setValueAtTime(v, time)`,
не `gain.gain.value = v`.** Клик (см. ниже) планируется на будущее время
через lookahead (до 100ms вперёд в `schedule()`). Если задать `.value`
напрямую, автоматизация стартует от «сейчас», а не от `time` — к моменту
реального `start(time)` экспоненциальный спад уже почти долетел до нуля,
и звук получается не слышен. Один раз уже наступали на это в `clickSound()`.

**Сетка долей секции песни** (`screens/songScreen.ts`, `.bar-grid`) —
возвращена из v1 (`SectionCard.tsx`): в каждой карточке секции квадратик на
долю (`bars × beatsPerBar`, доли — из метронома, в строке — целые такты, до
8 квадратиков), первая доля такта отмечена. Во время игры прошедшие доли
закрашены, текущая выделена, карточка текущей секции — `.card--active`, и
экран доезжает до неё (`scrollIntoView`). Номер доли считается от начала
песни (`bar × beatsPerBar + beat − 1`), как в движке.

**Источник звука — на каждую долю** (`soundSourceAt()` в `audioEngine.ts`):
филл секции, покрывающий эту долю (поздний перекрывает ранний, обрезается
концом секции) → бит секции (по кругу от начала секции) → паттерн песни
(по кругу от начала песни). Шагов на долю — `Pattern.stepsPerBeat` (у бита
— M его размера N/M, у паттерна песни — 2, восьмые). `patternStep` в
событиях — только для паттерна песни (его подсвечивает редактор паттерна и
плейхед редактора бита), для бита/филла секции `-1`. Тест — последние в
`tests/audioEngine.test.ts`.

**Движок держится в курсе правок загруженной песни** (`app.ts`,
`engineSongId`/`engineSong`/`engineBeats` + `subscribe`): `loadSongIntoEngine()`
задаёт, какую песню играть, а секции, паттерн и биты приходят и меняются
позже (в том числе из Firestore после обновления страницы) — без
пересинхронизации движок играл старую версию (новая песня с одной вводной
«1 2 3 4» крутила только её). Движку уходит копия песни с подставленными
паттернами битов секций (`resolveSongForEngine()`, `data/resolveBeat.ts`) —
пересобирается при изменении и песни, и битов (правка бита в «Битах» сразу
слышна в песне). Каждое сохранение — новый объект, поэтому «изменилась» =
другая ссылка. `syncEngineSong()` сама подписчик состояния — `patchState`
в ней только ПОСЛЕ того, как запомнила отданную версию, иначе бесконечная
рекурсия (уже наступали). Вход в редактор бита обнуляет `engineSongId` —
там движок играет бит.

Экраны на сброс позиции смотрят на `engine.isPlaying`, поэтому движок при
остановке (и ручной, и по концу песни) сначала ставит `isPlaying = false`,
потом сбрасывает позицию. По концу песни раньше было наоборот — экраны
принимали сброс за «играет, такт 0, доля 1» и оставляли подсветку.

### Кольцо метронома (dial)

`components/beatRing.ts` + `.dial`/`.dial__dot*` в `design/components.css`.
Термины (несколько раз путались раньше — не путать при правках):
- Весь круг целиком — один такт.
- Крупные точки (`--large`) — доли такта, `beatsPerBar` (12/3/6/9 часов
  при 4 долях).
- Мелкие точки (`--small`) — деление доли, `beatDivision`: сколько ударов
  умещается в одну долю, точки лежат МЕЖДУ соседними крупными.
- Размер «4/4» = `beatsPerBar=4, beatDivision=4` — это ровно тот случай,
  когда клик, мигание и (при «Считать вслух») счёт совпадают на каждой
  точке круга, крупной и мелкой одинаково.

Заливка кольца (`.dial--flash`) и закраска точек (`.dial__dot--filled`)
копятся весь такт и разом гаснут в начале следующего (см. `filled: Set`
в `beatRing.ts`, очищается на `beat === 1 && subBeat === 0`) — это НЕ
одна бегущая точка/вспышка, которая гаснет сама по себе.

Звук (`clickSound()` в `audioEngine.ts`) — синтезированный осциллятор, не
сэмпл: акцент на каждую долю (крупная точка), обычный клик на каждый удар
деления (мелкая точка). Раньше деление было чисто визуальным — теперь
звучит тоже, но только в режиме простого клика (не в паттерне, не при
«Считать вслух» — там на его месте, соответственно, паттерн-сэмплы или
голос).

### Библиотека битов и брейков (для барабанщика)

Страница `/beats`, `/beats/:id` — короткие кастомные паттерны (до 128
шагов), хранятся в аккаунте (`users/{uid}/beats`), назначаются в секции
песни (бит секции, филлы — см. ниже). Два ключевых архитектурных решения, которые
важно не сломать при правках:

**Роль ≠ сэмпл.** `Beat.tracks[].role` — одна из 8 фиксированных ролей
(`DRUM_ROLES` в `config.ts`: kick/snare/hihat/tom1/tom2/tom3/crash/ride), не
сэмпл напрямую. Реальный файл даёт «кит» (`DRUM_KITS`, сейчас `real` и
`pearl` — оба реально доступных кита в `public/sound/`). `data/resolveBeat.ts`
конвертирует `Beat` в обычный `Pattern`/`PatternTrack` (резолвя роль → сэмпл
через кит) прямо перед `engine.setSong(...)` — поэтому `audioEngine.ts` про
`Beat`/`DrumKit` вообще не знает и не менялся. Кит выбирается на самом бите
(`Beat.kitId`, не общая настройка приложения) через «Sound» в редакторе —
план `playful-snacking-mountain.md` в истории изначально откладывал этот
выбор в UI, добавлено следующим шагом сразу после.

**Длина бита — свободная, в шагах: `Beat.steps` (1..`BEAT_MAX_STEPS` = 128),
не в тактах** — как у референса (realdrummetronome.com/editor), решение
пользователя. Шаги добавляются/удаляются по одному («+» справа от сетки,
корзина под каждым столбцом, тап по «призрачному» столбцу за концом, копия
вправо/вставка за концом). Раньше длина хранилась целыми тактами
(`Beat.bars`) — `normalizeBeat()` (`data/beatsLibrary.ts`) пересчитывает.

**Размер бита «доли × удары» (N/M = `beatsPerBar` долей по `beatDivision`
клеток) — определяется по числу столбцов автоматически, весь бит — один
такт** (`data/beatMeter.ts`, решение пользователя): делится на 4 → N/4;
иначе на 3 → N/3; иначе N = наименьший простой множитель (простое → 1/число):
4 = 1/4, 6 = 2/3, 8 = 2/4, 10 = 2/5, 16 = 4/4, 7 = 1/7. Кратные 12
неоднозначны (12 = 3/4 или 4/3) — только тогда над сеткой переключатель
(`.dial__meter--active`), выбор держится, пока длина допускает его.
Пересчёт — в `onEdit` редактора на каждое изменение длины. **Шаг бита
звучит как 1/M доли** (`Pattern.stepsPerBeat = beatDivision`), бит на N/M
в песне занимает ровно N долей. Номеров тактов в сетке нет (бит = такт),
линия отмечает конец бита. `Pattern.steps` в `resolveBeat.ts` = `beat.steps`, не
`PATTERN_STEPS` (та фиксированная на 16 модель — для `Song.pattern`, другое;
один раз уже разошлось и играло не в такт).

**Бит играет ровно `beat.steps` шагов по кругу — поэтому в движок он уходит
БЕЗ секций** (`sections: []` в `syncEngine()` редактора). С секцией движок
обрывал круг на конце «песни», считанной в СВОИХ тактах (доли × 2 шага,
например 8): 7 шагов играли как `0123456 0123456 01 | 0123456…`. Не
возвращать туда секцию; тест — последний в `tests/audioEngine.test.ts`.

**Биты и филлы в секциях песни.** `Section.beatId` — бит из библиотеки как
грув на всю секцию вместо паттерна песни (выбор «Бит секции» в форме
секции). `Section.fills: { at, beatId }[]` — филл с доли `at` (от начала
секции, с 0): тап по квадратику-доле в сетке секции (`songScreen.ts`) →
выбор бита; доли под филлом — `.bar-grid__cell--fill`. В песне только
ссылки; `groove`/`fillPatterns` в `Section` — поля копии для движка
(`resolveSongForEngine`), в БД не пишутся. Удалённый бит — «бит удалён»,
секция играет паттерн песни. Удалить бит из UI сейчас нельзя (кнопку
убрали), общий доступ к битам — отложен.

**Сетка — `components/beatGrid.ts`, копия сетки референса и её поведения**
(изучено вживую и по их JS-бандлу): строки — SVG-иконки ролей
(`components/drumIcons.ts`, тап — прослушать через `engine.previewSound()`),
«+» под ними — добавить строку, корзина в конце строки — удалить; лента
столбцов 44×32px с горизонтальной прокруткой. Выделение — прямоугольник
(строки × шаги): мышью протянуть, на тачскрине подержать 350ms и вести
(просто провести — прокрутка). Тулбар над выделением: копировать / копия
влево / копия вправо (перезаписывают вплотную, выделение едет на копию) /
залить строки (повтор по всей длине с сохранением фазы) / отмена; Esc, ⌘C,
Enter. Вставка — полупрозрачный блок за курсором на любые строки, клик
(на тачскрине — кнопка в тулбаре), повторно до отмены, красная рамка — не
влезает по высоте. Подсветка играющего шага — напрямую в DOM
(`grid.setPlayhead`). Включённая нота всегда сразу звучит — у референса
это переключатель «Play sound on cell click», у нас он убран, всегда вкл.

Сетка — **один живой элемент на весь экран**: `beatEditorScreen.ts`
перерисовывает только блоки над/под ней, а ей отдаёт свежий бит через
`grid.update()`. Не возвращать её в общий `mount()` экрана — на каждый тап
терялись бы прокрутка ленты и захват указателя посреди выделения. Правки
сетка не сохраняет сама — отдаёт `{ steps, tracks }` через `onEdit`.


### Данные и синхронизация (Firebase: вход через Google + Firestore)

**Всё — в аккаунте пользователя.** Вход через Google (`data/auth.ts`,
`signInWithPopup`), Firebase помнит его между запусками. Без входа экраны
плейлиста и битов показывают карточку входа (`components/signInCard.ts`,
`accountGate()`), метроном работает и без входа. Коды плейлистов, общий
доступ группы и передача битов по коду **убраны и отложены** — решение
пользователя, к ним вернёмся отдельной задачей.

Firestore (`data/userLibrary.ts`):
- `users/{uid}` → `{ lastPlaylistId }` — последний плейлист открывается сам
  один раз при входе (`appState.applyCurrentPlaylist`, флаг `autoOpenDone`).
- `users/{uid}/playlists/{id}` → `{ name, songs, createdAt, updatedAt }`.
- `users/{uid}/beats/{id}` → `Beat` + `updatedAt`.

Запись — с дебаунсом `CONFIG.SAVE_DEBOUNCE_MS`, конфликт — last-write-wins.
Пока у документа идёт таймер дебаунса, снимок `onSnapshot` его версию не
берёт (держит локальную) — иначе снимок от соседней записи откатывал бы
только что сделанные тапы. Перед выходом из аккаунта — `flush()` (после
`signOut` прав на запись уже нет): `appState.signOut()`.

`firebase.ts`: Firestore с `persistentLocalCache` (PWA работает офлайн на
кэше) и `ignoreUndefinedProperties` (необязательные поля моделей бывают
`undefined` — без этого Firestore отказывается писать документ).

**Правила Firestore** (только в консоли, не в репозитории):
```
match /users/{uid}/{document=**} {
  allow read, write: if request.auth != null && request.auth.uid == uid;
}
```
В консоли также: Authentication → Google включён, Authorized domains —
домен Hostinger (localhost есть по умолчанию).

**Риск — вход на iPhone из иконки на экране «Домой»**: всплывающее окно в
такой PWA может не сработать, а вход через перенаправление в Safari сломан
для сайтов не на Firebase Hosting. Если не заработает — разместить служебные
файлы входа Firebase на нашем домене (документированный Firebase способ).

**Перед первым использованием** — обязательно заполнить
`src/data/firebaseConfig.ts` данными реального Firebase-проекта (инструкция
в комментарии в файле). Без этого `getDb()` бросает понятную ошибку, а
экраны аккаунта показывают подсказку вместо падения.

### PWA / прекеш

`vite.config.ts` → `vite-plugin-pwa`, `globPatterns` держится в синхроне
со списком реально используемых сэмплов в `src/config.ts`
(`ALL_INSTRUMENTS`) — добавили новый сэмпл в код, добавьте и в
`globPatterns`, иначе он либо не прекешируется (обычно не страшно — просто
не будет работать офлайн до первой загрузки онлайн), либо, если убрали из
кода но не из `globPatterns`, сборка предупредит, что паттерн ничего не
поймал.

## Деплой

Один workflow (`.github/workflows/deploy.yml`): typecheck + `npm test` +
`vite build` + SCP `dist/` на тот же Hostinger-домен, что и в v1
(`slateblue-crow-206906.hostingersite.com`). Бэкенда больше нет — значит
нет pm2, нет PHP-прокси, нет отдельного серверного деплоя.

`public/.htaccess` — SPA-fallback для самописного роутера (без него
обновление страницы на `/playlist` или `/song/:id` даст 404 от Apache
вместо `index.html`). Он же означает, что `/api/...` и вообще любой
несуществующий путь тоже вернёт `index.html` с 200 — это нормально,
проверять деплой по факту (что в `index.html`/бандле), а не по статус-коду.

**После любого деплоя браузер может показывать старую версию** —
PWA (`vite-plugin-pwa`, `registerType: 'autoUpdate'`) кэширует себя через
Service Worker. Смотрите не только на сервер (`curl`/содержимое
`dist/index.html`), а и на то, что реально отдаёт браузеру SW. Сброс:
DevTools → Application → Service Workers → Unregister → Cmd+Shift+R,
или просто открыть в приватном окне (это уже было граблями в v1).

SSH-доступ и структура `~/domains/<домен>/public_html` — как в v1
(см. `git log` до `v2 reset`, если нужны детали восстановления доступа).
